# Quickstart (TL;DR)

**Prepare the Software Environment**
Before running benchmarks, you must cross-compile the FFTW library for bare-metal RISC-V. A helper script is provided to automate this:
```bash
./setup_fftw.sh
```

#### Option A: Fast Software Simulation (Default Rocket Core)
The fastest way to verify the benchmark is running it through the Verilator software simulator using the default Chipyard configuration.

```bash
# 1. Compile the hardware simulator
make -C chipyard/sims/verilator CONFIG=RocketConfig

# 2. Compile the bare-metal C benchmark
make -C chipyard/tests fft_benchmark.riscv

# 3. Execute the simulation
./chipyard/sims/verilator/simulator-chipyard.harness-RocketConfig ./chipyard/tests/fft_benchmark.riscv
```

#### Option B: FPGA Bitstream Generation (Custom DSE)
To explore custom configurations and synthesize a physical bitstream for the Xilinx VC707:

```bash
# 1. Generate the custom architecture space
./rocket_fpga_dse.py generate

# 2. Kick off Vivado bitstream compilation
./rocket_fpga_dse.py build DSERocketConfig0

# 3. Compile the bare-metal C benchmark for the FPGA
make -C chipyard/tests fft_benchmark.riscv

# 4. (Deploy) Flash the bitstream to VC707 via Vivado and connect over UART (115200 or 921600 baud)
```

## Prerequisites
Before running the DSE pipeline, ensure your server has the following installed:
* **OS:** Ubuntu 20.04 or 22.04 LTS (Recommended)
* **FPGA Toolchain:** Xilinx Vivado 2022.2+ (Required for VC707 bitstream generation)
* **Environment:** Conda (for Chipyard dependency management)
* **Compiler:** `riscv64-unknown-elf-gcc` (Included via Chipyard toolchain build)

1. Integration: Place C source in chipyard/tests.

```bash

PROGRAMS = pwm blkdev accum charcount nic-loopback big-blkdev pingd \
           streaming-passthrough streaming-fir nvdla spiflashread spiflashwrite fft gcd \
           hello mt-hello symmetric fft_dummy fft_benchmark \ 
           <your_binary/.o>

```

```bash
    cmake -S ./ -B ./build/ -D CMAKE_BUILD_TYPE=Debug
    cmake --build ./build/ --target all
```
    
#### Simulation Execution:
```bash
./simulator-chipyard.harness-<ConfigName> +permissive +dramsim \
+dramsim_ini_dir=../../generators/testchipip/src/main/resources/dramsim2_ini \
+max-cycles=10000000 +permissive-off ../../tests/build/<binaryName>.riscv
```

## Bare-Metal Software Deployment

Standard C libraries (`<stdio.h>`, `<stdlib.h>`) rely on Linux system calls (ECALL), which will crash on a bare-metal FPGA. To execute complex benchmarks like FFT, we use a custom bare-metal environment located in `chipyard/tests/`.

### Memory-Mapped UART (printf)

To extract data from the physical FPGA, we utilize a lightweight formatter (mpaland/printf) mapped directly to the VC707's hardware UART register.

* **Base Address:** The SiFive UART on our Rocket configuration is located at `0x10020000`.
* **Hardware Initialization:** The UART transmitter is enabled by writing `1` to the `TXCTRL` offset (`0x08`).
* **High-Speed Baud Rate:** To mitigate I/O bottlenecks during simulation and FPGA execution, the hardware is configured via `WithUARTInitBaudRate(921600)`. When connecting to the FPGA via a host serial terminal (e.g., `screen` or `minicom`), the connection must be explicitly set to **921600 baud** (not the standard 115200) to prevent corrupted character output.
### Dynamic Memory (malloc)

To support heavy workloads like FFTW, dynamic memory allocation is supported via Newlib. A custom `_sbrk` function (in `syscalls.c`) acts as a bump-allocator, providing `malloc` access to the continuous unused DDR3 RAM space starting at the linker script's `_end` boundary.

### Cross-Compiling FFTW for Bare-Metal

FFTW is highly dependent on an operating system. To compile it for a bare-metal RISC-V core, it must be configured to strip OS dependencies (threads, shared libraries) and use position-independent memory addressing (`medany`) so it can reside safely in DDR3 RAM at `0x80000000`.

```bash
# Download and extract
wget http://www.fftw.org/fftw-3.3.10.tar.gz
tar -xvzf fftw-3.3.10.tar.gz && cd fftw-3.3.10

# Cross-compile with OS-stripping and medany flags
./configure --host=riscv64-unknown-elf \
            CC=riscv64-unknown-elf-gcc \
            CFLAGS="-O2 -mcmodel=medany" \
            --disable-shared \
            --enable-static \
            --disable-threads \
            --disable-fortran

make -j$(nproc)
```

*(Copy the resulting `libfftw3.a` and `fftw3.h` into the `chipyard/tests/` directory.)*

### Linking External Static Libraries (Makefile Override)

Standard Chipyard Makefiles process dependencies sequentially from left to right. Because of this, external libraries must be explicitly placed at the end of the linker command to prevent "undefined reference" errors.

To link FFTW, add a custom target override to `chipyard/tests/Makefile`:

```makefile
# Custom override to enforce strict Linker Order for FFTW
fft_benchmark.riscv: fft_benchmark.o $(libgloss)
	$(GCC) $(LDFLAGS) $< -o $@ -L. -lfftw3 -lm
```

- `-L.`: Searches the current directory for library archives.
- `-lfftw3`: Links the static `libfftw3.a` archive.
- `-lm`: Links the standard math library (required for hardware sine/cosine).

### Simulator Workload Tweaks

Running complex bare-metal code in Verilator requires two safety traps to prevent simulator crashes:

- **The ESTIMATE Trap**: Always use `FFTW_ESTIMATE` when generating plans. Using `FFTW_MEASURE` will cause the 50MHz simulated CPU to spend weeks endlessly looping to benchmark the math path.
- **The Physics Delay Loop**: Add an empty delay loop (`for (volatile int i = 0; i < 2000000; i++);`) before `return 0;`. This prevents the simulator's `$finish` command from shutting off the virtual silicon before the slow 115,200 baud UART hardware finishes transmitting text.


## FFTW and Edge Detection Metrics

The files for this experiment are in the `tests/` folder of this repository. Copy them into `chipyard/tests/` before running the experiment.

The following files must be in the same `chipyard/tests/` directory:

- `fft_metrics.c`: measures FFTW planning and execution separately.
- `edgeBare_metrics.c`: measures the Sobel edge-detection loop.
- `image.py`: converts one image into `image_data.h`.
- `run_metrics.py`: builds and runs every benchmark in sequence.
- `plot_metrics.py`: averages the results and creates the plots.

Copy these input folders into `chipyard/tests/` as well:

- `32x32/`
- `64x64/`
- `128x128/`
- `256x256/`

Each folder contains the same four test images at that resolution. The pipeline generates `image_data.h` for one image, compiles both programs with that header, and then moves to the next image.

### Makefile changes

Add both programs to `PROGRAMS` in `chipyard/tests/Makefile`:

```makefile
PROGRAMS += edgeBare_metrics fft_metrics
```

Add these build rules:

```makefile
edgeBare_metrics.riscv: edgeBare_metrics.o $(libgloss)
	$(GCC) $(LDFLAGS) $< -o $@ -lm

# Rebuild both programs whenever image.py creates a new image_data.h.
edgeBare_metrics.o fft_metrics.o: image_data.h

fft_metrics.o: fftw3.h

fft_metrics.riscv: fft_metrics.o libfftw3.a $(libgloss)
	$(GCC) $(LDFLAGS) $< -o $@ \
		-Wl,--defsym=__heap_size=0x4000000 \
		-L. -lfftw3 -lm
```

The normal Chipyard test flags are used:

```makefile
-O2 -mcmodel=medany -march=rv64imafdc -mabi=lp64d -static
```

The added linker options are:

- `-lm` for the math library.
- `-L. -lfftw3` for `libfftw3.a` in `chipyard/tests/`.
- `-Wl,--defsym=__heap_size=0x4000000` to give FFTW a 64 MiB heap.

Both `fftw3.h` and `libfftw3.a` must also be present in `chipyard/tests/`.

### OwnMemoryRocketConfig

Add this configuration to `chipyard/generators/chipyard/src/main/scala/config/MemorySystemConfigs.scala`:

```scala
class OwnMemoryRocketConfig extends Config(
  new freechips.rocketchip.subsystem.WithoutTLMonitors ++
  new freechips.rocketchip.subsystem.WithExtMemSize((1 << 30) * 1L) ++
  new freechips.rocketchip.subsystem.WithNBigCores(4) ++
  new freechips.rocketchip.subsystem.WithNMemoryChannels(4) ++
  new chipyard.config.AbstractConfig)
```

This configuration has four Rocket cores, four memory channels, and 1 GiB of external memory. TileLink monitors are disabled to reduce simulation overhead.

### Run the pipeline

The pipeline uses the `OwnMemoryRocketConfig` Verilator simulator. Build it once after adding the configuration:

```bash
cd chipyard
source env.sh
make -C sims/verilator CONFIG=OwnMemoryRocketConfig
```

Run all 32 benchmarks with:

```bash
cd chipyard
source env.sh
python3 -u tests/run_metrics.py | tee tests/metrics_pipeline.log
```

The pipeline runs four images at four resolutions with two algorithms:

```text
4 images x 4 resolutions x 2 algorithms = 32 runs
```

It saves the raw program output and simulator diagnostics in `tests/metrics_results/`. The C programs record cycles and retired instructions. The Python pipeline converts cycles to target time using the 500 MHz core clock and records the full Verilator host time separately.

Create the averaged CSV file and plots with:

```bash
cd chipyard
source env.sh
python3 tests/plot_metrics.py
```

The generated files are stored in `tests/metrics_plots/`. This repository also includes the raw results and generated plots from the completed experiment.
